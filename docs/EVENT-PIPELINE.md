# Event reconciliation

The development platform now separates durable receipt from projection. POST `/integration/events` returns 202 after committing an authenticated controller's event. POST `/integration/process` projects up to 100 available messages. The existing single-worker runner also processes inboxes. GET `/integration/status` shows gaps, conflicts, failures and backlog; GET `/integration/outbox` exposes immutable local projection notifications for future dispatch.

An envelope has entity_id, connection_id, event_id, external_id, version, operation (upsert/delete/restore), occurred_at (timezone-aware ISO timestamp), reason, and journal for upsert/restore. The journal external_id and version must match the envelope. The existing canonical JournalInput account and money rules apply. Versions start at 1 per entity/connection/source identity and advance consecutively. occurred_at is provenance, never a last-write-wins ordering key. Use an adapter to translate a source's CDC position into this per-record version sequence; opaque provider log offsets are not themselves canonical record versions.

Same connection/event ID and same normalized envelope hash returns replayed=true. Different content returns 409. Different event IDs targeting the same source version still face immutable source-hash comparison. Higher versions wait for missing predecessors. Conflicting versions are quarantined; validation failures retry to three attempts and then dead letter. After fixing mappings, controllers can explicitly retry a validation failure. Conflicting source content requires source-authority arbitration and a new correctly ordered revision; the platform does not silently replace it.

Projection, source versions, audit entry, inbox status and outbox insertion commit together. Each message uses a savepoint so one failure does not erase other valid projections. PostgreSQL processing locks the organization row; SQLite requires one writer/worker. Financial versions stay deterministic and balanced. This implements idempotent local business effects under replay; it does not promise exactly-once network delivery.

Deletion appends an immutable SourceRecord tombstone and excludes the source from active reports. Original journals/lines stay available in history. Tombstones and deduplication keys have no automatic TTL or purge: retention requires approved policy and a verified replay/synchronization boundary. Ordinary imports cannot resurrect deleted sources. A controller must submit an explicit restore event with the next version and balanced journal. Deletion represents upstream lifecycle invalidation, not a legal accounting reversal; posted accounting corrections should use an approved reversal journal. Independent approval is supported for journal adjustments, but lifecycle events currently require a controller and do not have a second-review gate.

The screen reports completeness of received events only. Upstream missing events cannot be inferred. A caught-up backlog does not certify complete ERP extracts or a statutory close. Preserve closed report snapshots and inspect unresolved events before signoff. Separate sources are never automatically merged based on similar names or amounts. Financial amounts use no CRDT arithmetic; cross-source duplicates remain review hypotheses.

Still required for a production deployment: source-specific live CDC subscriptions, broker transport and acknowledgement dispatcher, per-source checkpoint reconciliation, consumer leases and concurrent load/fault testing, alerting/SLOs, controlled conflict resolution tooling, source retention agreements, and close signoff gates tied to certified source completeness. The local outbox is inspectable, not an external message publisher. Existing Business Central and NetSuite connectors remain bounded snapshot readers.

The user-supplied research informed the architecture. Reported research throughput, savings and clinical reconciliation statistics are not platform benchmarks, finance-domain validation, or implemented guarantees.
