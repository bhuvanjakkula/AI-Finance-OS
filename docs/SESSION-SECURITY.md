# Account session security — 11 October 2026

Organization now includes Your active sessions for every signed-in role. Users can list their unexpired sessions, identify the current session, revoke an individual session or sign out all other sessions. Controls only act on the signed-in user's account. Expiry timestamps include UTC offsets in the API and display in the browser's local timezone.

GET /auth/sessions returns opaque public identifiers, expires_at and current. Identifiers are SHA-256 domain-separated derivatives of stored token hashes; raw bearer tokens and their storage hashes are never returned. POST /auth/sessions/{id}/revoke accepts the public identifier. Clients must fetch fresh identifiers; previous storage-hash identifiers are no longer accepted. POST /auth/sessions/revoke-others preserves the caller's current session and deletes other sessions for that user, including expired records. Revocations and logout create audit events in the existing chain. No database migration is required.

Authorization checks look up the session on each API request. A revoked session fails its next authentication check; a request already in progress is not canceled. No device/IP tracking or identity verification is implied. Possession of a bearer token still authorizes session management; MFA, step-up authentication, distributed login abuse protection and enterprise SSO remain future work. This update is not a penetration test or security certification.

Verification: 50 backend tests pass, with one existing Starlette/httpx deprecation warning; production frontend build passes. Tests cover current-session labeling, non-exposure of stored hashes, cross-user isolation, auditor access, expired-session exclusion, individual/bulk revocation, immediate authentication rejection, audit events and repeated revocation. Browser signed into the synthetic QA workspace, listed four sessions and revoked three older sessions while preserving the current session. Real user sessions were not used for that browser test.
